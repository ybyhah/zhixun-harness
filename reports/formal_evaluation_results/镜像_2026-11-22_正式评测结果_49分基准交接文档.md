## 1. 项目背景与当前状态

本项目是面向工业模型持续优化的 Harness。它在平台正式 SDK 提供的历史、模型和候选提交接口上，循环完成“读取历史 → 提出假设/超参数 → 训练官方基线的续训候选 → 提交候选 → 读取平台指标 → 门控选择 → 记录审计 → 结束”。目标不是离线训练一个固定模型，而是在 A/B/C 三个工业任务上无人干预地进行受控自改进，并保留可复现的训练证据。

截至镜像 `zhixun-submit:linux-amd64-20261122`，正式提交外壳、平台指标闭环、A/B/C 策略、审计字段、Docker 打包和基础测试均已形成。Qwen 通过平台运行时 `rnd.model()` 接入，模型 ID 由平台环境提供；本地 `decision.py` 只用于诊断或平台调用失败时的保守回退，不应被描述为正式评分依据。

镜像 tar 已验证为单个 Linux/amd64 Docker 镜像，约 71 MB；镜像不打包数据集、权重或密钥，运行时由平台挂载/提供。

## 3. 历史修改记录

### 3.1 正式 SDK 闭环与平台指标门控

早期实现从本地指标或规则结果推断候选是否上线，无法证明平台真实计量。后续将正式路径固定为：`rnd.history()` 读取平台历史，`rnd.model()` 调用 Qwen，训练候选后调用 `rnd.submit_candidate()`，只使用返回的 `submitted["summary"]["metrics"]` 进行选型，最后调用 `rnd.finish()`。这解决了“本地看起来提升、平台实际不认”的根本问题。

涉及：`submission/contest_submission.py`、`contest-harness-sdk-1.0.2/`、协议测试。

### 3.2 A/B/C 策略和安全回退

- A：前两轮采用已验证的强起点（10 epochs、学习率 0.01），之后再使用 Qwen 建议；Macro-F1 的最小增益和 Accuracy 下限用于抑制小幅追涨。
- B：首轮使用稳定配置；出现停滞时在未尝试的配置轴之间切换，并重置优化器动量，避免 Adam 状态把模型锁在平台期。
- C：保留安全回退，候选必须同时满足平台主指标要求；NASA 相关退化超过阈值时 veto，并恢复历史最佳父模型。

涉及：`submission/contest_submission.py`、`submission/baselines/train.py`。

### 3.3 资源效率与闭环审计

在完成足够闭环、近期连续拒绝且没有有害漂移时，B 允许跳过低价值训练并保留父模型；每轮写入假设、参数、选择理由、提交结果、平台指标、是否上线、回退和漂移字段。该设计用于提高资源效率并支撑正式评分中的可追溯性。

### 3.4 C 的平台反馈搜索

C 的本地 RMSE 与 NASA 指标可能出现方向冲突，后续策略使用平台返回的历史反馈限制重复父模型/重复学习率组合，并对 NASA 退化执行保守拒绝。该措施优先保护隐藏集上的安全性，而不是单纯追逐本地 RMSE。

### 3.5 镜像与交付

正式镜像采用 `submission/Dockerfile`，使用 Linux/amd64，运行时不依赖仓库外的源码路径；数据、权重和密钥不打包。最终交付物是单个未压缩 tar，而不是 ZIP、源码压缩包或 gzip。

## 4. 有效经验

1. 平台返回的 summary/metrics 必须是唯一上线依据；本地验证只能用于诊断，不能替代平台计量。
2. 每轮都保留父 checkpoint；候选被拒绝时不覆盖 best，下一轮从最后一个被采纳版本继续。
3. A、B、C 应使用不同的策略与门控，不能用一个通用学习率搜索器覆盖三个任务。
4. C 采用多指标安全门控比单看 RMSE 更可靠，特别是存在 NASA 惩罚或寿命高估风险时。
5. B 发生策略切换时重置优化器状态，通常比持续沿用旧动量更容易突破停滞。
6. 审计记录必须写入平台指标、假设、参数、理由、call ID/降级状态和最终选择；只有运行日志而没有结构化字段，无法证明闭环。
7. 正式镜像和本地开发镜像必须分开；构建上下文要排除数据、权重、`.env` 和临时实验输出。

## 5. 收益、损失与教训

| 做法 | 收益 | 代价/教训 |
|---|---|---|
| 改用平台 summary 指标门控 | 解决本地指标与隐藏评测脱节，符合 SDK 契约 | 本地不能单独预测最终得分，必须消耗平台试运行验证 |
| B 策略切换并重置动量 | 减少连续停滞，后续试运行恢复了 B 的表现 | 训练配置变多，必须禁止重复父模型+重复超参组合 |
| C NASA 安全 veto 与回退 | 防止一次候选改善 RMSE 却造成安全指标恶化 | 可能拒绝看似更优的候选，平均性能提升会变慢 |
| 资源跳过 | 降低无效训练时间和 token/CPU 消耗 | 闭环不足或漂移依赖未启用时不能误跳过，否则会影响恢复分 |
| 完整审计字段 | 便于复盘和平台评分证明 | 字段缺失会使“实际调用了 Qwen”无法举证 |
| 仅提交 amd64 tar | 符合服务器格式检查 | Windows 本地构建必须明确指定 `--platform linux/amd64` 并用 `docker save` |

最重要的失败教训是：本地 A/B/C 训练成功不等于平台得分成功；C 曾出现 RMSE 与 NASA 方向冲突，正式评分中最差阶段和资源效率仍然可能为低分。因此任何新策略都应先验证正式 SDK 的上报字段、平台摘要解析和回退行为，再讨论模型参数优化。

## 6. 当前遗留问题与风险

- 正式评分中曾出现 objective 11.608652/35、平均性能 2.640398/15、最差阶段 0/5、恢复 3.968254/5、稳定性 5/5、资源效率 0/5；说明稳定性较好，但最差阶段、平均提升和资源效率仍是主要失分点。
- C 的多目标门控保护了 NASA，但可能牺牲 RMSE 平均提升；隐藏测试集与本地 test 集存在偏差，不能仅凭本地结果选参数。
- 低价值轮次跳过依赖“至少 3 条完整闭环、近期拒绝且无有害漂移”等前提；平台历史字段缺失或漂移依赖未启用时，必须保守训练/回退。
- Qwen 的真实 endpoint、模型 ID、call ID 由平台提供；本地没有独立可验证的 API 密钥。不要把本地规则降级误写成 Qwen 成功调用。
- 交付 tar 是 2026-11-22 边界版本；当前工作区可能存在 11-24 之后未纳入该镜像的代码、文档或实验产物，不能混合宣称为交付版本。
- 未经验证不要修改正式 SDK 入口、`PREDICT_ARGV`、Docker ENTRYPOINT、提交协议字段或 checkpoint 目录结构。

## 8. 下一步建议

### P0：提交前必须确认

1. 用最终 tar 在 Linux/amd64 环境 `docker load` 并执行平台提供的 smoke test。
2. 检查镜像中 `decision.py`、正式入口和预测命令均可用，且不存在 `ModuleNotFoundError`。
3. 确认每个 A/B/C 任务至少有 3 条完整闭环审计，包含平台指标、选择理由和 call ID/降级状态。
4. 确认提交材料只上传单个未压缩 tar，并附源码仓库、作品文档和 SwanLab 记录链接。

### P1：提升客观分

1. 优先优化最差阶段和恢复速度：平台拒绝后保留最佳父模型，缩短恢复到可接受指标的轮数。
2. C 继续使用安全多指标门控，记录 RMSE、NASA、高估率和回退原因，避免单指标优化。
3. B 保留稳定策略，比较策略切换是否真正改善隐藏集，而不是扩大搜索空间。
4. 在满足闭环前提下再启用训练跳过；把跳过轮计入审计并明确其资源收益。

### P2：证据与复现

1. 生成统一客观评分代理表：平均提升、最差阶段、恢复轮数、稳定性、资源消耗、采纳率。
2. 固定 Python、Docker、SDK、模型 ID 和镜像 digest，保存最终提交命令。
3. 更新 `作品文档.md` 时注明“平台指标优先、本地结果仅作诊断”，避免答辩材料与实际行为不一致。

## 9. 交接结论

2026-11-22 镜像已经具备可提交的正式 SDK 外壳和 A/B/C 受控优化框架；下一位 AI 不应从头重写 Harness，而应围绕平台真实 summary、最差阶段恢复、C 的安全门控和资源效率做小步、可回滚的实验。所有结论必须以平台隐藏测试反馈为准。
